# React + TypeScript + Vite

This template provides a minimal setup to get React working in Vite with HMR and some Oxlint rules.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Oxc](https://oxc.rs)
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/)

## React Compiler

The React Compiler is not enabled on this template because of its impact on dev & build performances. To add it, see [this documentation](https://react.dev/learn/react-compiler/installation).

## Expanding the Oxlint configuration

If you are developing a production application, we recommend enabling type-aware lint rules by installing `oxlint-tsgolint` and editing `.oxlintrc.json`:

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "plugins": ["react", "typescript", "oxc"],
  "options": {
    "typeAware": true
  },
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": ["warn", { "allowConstantExport": true }]
  }
}
```

See the [Oxlint rules documentation](https://oxc.rs/docs/guide/usage/linter/rules) for the full list of rules and categories.

## Голосовые сообщения и медиа

- Кнопка микрофона записывает голосовое сообщение через `MediaRecorder`; перед отправкой запись можно отменить.
- Поддерживаются изображения, MP4/WebM/MOV-видео, аудио, PDF, TXT/CSV, ZIP и документы Microsoft Office.
- Максимальный размер одного вложения — 25 МБ.
- Тип, исходное имя, размер и длительность голосового хранятся в `messages.attachment_meta`.
- Миграция колонки выполняется автоматически при запуске сервера.

## Хранение загруженных файлов

Аватары, голосовые и остальные вложения сервер кладёт в `UPLOADS_DIR` (по умолчанию `server/uploads`).
На хостингах с одноразовой файловой системой — Railway, Render, Fly — эту папку **обязательно**
нужно вынести на постоянный том, иначе при каждом деплое все загруженные файлы исчезают,
а в базе останутся ссылки на несуществующие картинки.

Как сделано на Railway: к сервису подключён том с точкой монтирования `/data`, а переменная
окружения задана как `UPLOADS_DIR=/data/uploads`.

```bash
railway volume add -m /data
railway variables --set UPLOADS_DIR=/data/uploads
```

Если картинка всё же не загрузилась, интерфейс показывает букву вместо значка битого
изображения (`src/components/AvatarImage.tsx`).

## Звонки

Один на один, WebRTC, аудио и видео.

**Что умеет**

- Приглашение приходит на все открытые вкладки, но как только звонок принят на одном
  устройстве, остальные перестают звонить, а сигналинг идёт только в принявший сокет.
- Пока идёт звонок, второй входящий автоматически получает «занято» — это проверяет сервер,
  а не только клиент.
- Камеру и демонстрацию экрана можно включить прямо в аудиозвонке: у соединения всегда есть
  видео-трансивер, а повторные переговоры идут по схеме perfect negotiation.
- Собеседник видит, что у вас выключен микрофон или камера и что вы показываете экран
  (событие `call_state`).
- Звонок можно свернуть в плашку и продолжать переписываться; медиаэлемент при этом
  не пересоздаётся, поэтому звук не прерывается.
- Микрофон, камеру и динамики можно выбрать заранее в настройках или переключить на лету
  во время разговора — дорожка подменяется без разрыва соединения.
- Индикатор качества связи считается по `getStats` (задержка, потери, битрейт), рядом
  показывается, кто говорит.
- Горячие клавиши: `M` — микрофон, `V` — камера, `Esc` — свернуть/развернуть.
- Пока идёт разговор, экран не гаснет (Wake Lock), а входящий звонок при скрытой вкладке
  подсвечивается в заголовке и системным уведомлением.

**История звонков**

Каждый звонок оставляет запись в чате: исходящий/входящий с длительностью, пропущенный,
отклонённый, отменённый. Записи создаёт сервер (`server/src/calls.js`), поэтому итог не зависит
от того, у кого раньше закрылась вкладка: обрыв сокета тоже корректно завершает звонок.
Записи хранятся в `messages` с `type = 'call'` и JSON-полем `call_meta`; миграция добавляется
автоматически при старте сервера.

### Настройка TURN-сервера

Аудио/видеозвонки используют WebRTC. По умолчанию доступны только публичные STUN-серверы Google — этого достаточно в большинстве сетей, но звонок может не установиться, если оба собеседника находятся за строгим NAT/симметричным файрволом (частая ситуация в мобильных и корпоративных сетях). Чтобы это исправить, добавьте на сервере (`server/`) переменные окружения TURN-релея:

```
TURN_URLS=turn:turn.example.com:3478,turns:turn.example.com:5349
TURN_USERNAME=имя_пользователя
TURN_CREDENTIAL=пароль_или_токен
```

- `TURN_URLS` — один или несколько адресов через запятую.
- Если переменные не заданы, сервер отдаёт клиентам только STUN — звонки продолжат работать как раньше.
- Учётные данные никогда не попадают в клиентский бандл: клиент получает список ICE-серверов с бэкенда через `GET /api/ice-servers` при каждом запуске.

Получить TURN-сервер можно, например, у [Twilio](https://www.twilio.com/docs/stun-turn), [Cloudflare Calls](https://developers.cloudflare.com/calls/), [Metered.ca](https://www.metered.ca/tools/openrelay/) (есть бесплатный лимит) или развернуть свой [coturn](https://github.com/coturn/coturn).

При кратковременных обрывах сети звонок пытается восстановиться сам: звонящая сторона запускает ICE restart, и есть 15 секунд на восстановление, прежде чем звонок завершится. В интерфейсе в этот момент видно «Восстановление соединения…».

### Email-алерты о падениях и подборе пароля

Сервер может слать письмо владельцу при аварийном завершении процесса (`uncaughtException`)
и при срабатывании блокировки аккаунта после подряд идущих неудачных попыток входа —
похоже на подбор пароля. Использует ту же почтовую инфраструктуру (`RESEND_API_KEY`/`MAIL_FROM`),
что и письма пользователям.

```
ALERT_EMAIL=you@example.com
```

Если переменная не задана — алерты просто не отправляются (сервер продолжает работать как раньше).
На каждый вид события — не чаще одного письма в 10 минут, чтобы не заспамить себя во время атаки.

### Двухфакторная аутентификация (TOTP)

Пользователи могут включить вход по коду из приложения-аутентификатора (Google Authenticator,
Aegis и похожие) в Настройки → Безопасность. Секрет хранится в базе зашифрованным
(AES-256-GCM) — для этого серверу нужен 32-байтный ключ:

```
TOTP_ENC_KEY=<64 hex-символа или 44 base64-символа>
```

Сгенерировать ключ:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Если переменная не задана — попытка включить 2FA вернёт понятную ошибку, остальной
функционал не затрагивается. **Ключ нельзя менять после того, как хотя бы один пользователь
включил 2FA** — иначе существующие секреты станет невозможно расшифровать, и им придётся
подключать 2FA заново.

## Push-уведомления

Уведомления через `new Notification()` живут ровно столько, сколько открыта вкладка —
закрытое приложение так уведомить нельзя. Для этого есть два транспорта под одним
API (`src/native/push.ts`), сервер различает их по полю `provider`:

- **Web Push (VAPID)** — браузеры и PWA, установленная на домашний экран iOS 16.4+;
- **APNs** — нативная сборка для iOS.

Устройства лежат в таблице `push_devices` и привязаны к сессии: выход, отзыв сессии,
смена пароля и протухание сессии по TTL забирают с собой и право слать на устройство пуши.
Пуш уходит только тем участникам чата, у кого нет живого сокета и у кого чат не в беззвучном
режиме. Текст сообщения сервер подставляет в уведомление только для нешифрованных чатов —
у E2E в базе лежит один шифротекст, и показать там нечего.

### Web Push

```
VAPID_PUBLIC_KEY=<публичный ключ>
VAPID_PRIVATE_KEY=<приватный ключ>
VAPID_SUBJECT=mailto:you@example.com
```

Пару ключей достаточно сгенерировать один раз:

```bash
node -e "console.log(require('web-push').generateVAPIDKeys())"
```

### APNs

Нужен ключ APNs (Apple Developer → Keys → создать ключ с доступом к Apple Push Notifications):

```
APNS_KEY=<содержимое .p8-файла>
APNS_KEY_ID=<10 символов, идентификатор ключа>
APNS_TEAM_ID=<10 символов, Team ID>
APNS_BUNDLE_ID=<bundle id приложения>
APNS_PRODUCTION=1
```

`APNS_BUNDLE_ID` обязан совпадать с `appId` в `capacitor.config.ts` и с Bundle Identifier
в Xcode, иначе APNs отвечает `BadTopic`. Без `APNS_PRODUCTION=1` используется sandbox —
туда попадают только сборки, установленные из Xcode напрямую; TestFlight и App Store
ходят в боевое окружение.

Если переменные не заданы, соответствующий транспорт просто выключен: уведомления
продолжают работать, пока приложение открыто.

Есть ещё `APNS_HOST` — он переопределяет адрес APNs. В бою его задавать не нужно; он
существует ради тестов, которые поднимают локальный мок вместо серверов Apple
(см. `server/test/callkit.test.js` и `.github/workflows/ci.yml`).

## Сборка приложения для iOS (.ipa)

Клиент упакован через [Capacitor](https://capacitorjs.com): ассеты собираются в бандл
приложения, а не грузятся с сервера — приложение открывается мгновенно и без сети.
Собрать `.ipa` можно только на macOS с Xcode; всё остальное готовится на любой системе.

### Что уже сделано в коде

- **Авторизация.** В WebView страница живёт на `capacitor://localhost`, и кука сессии
  с домена API туда не доходит. Нативному клиенту (заголовок `X-Client: native`) сервер
  отдаёт session token в теле ответа, клиент кладёт его в Keychain и ходит с
  `Authorization: Bearer`. WebSocket авторизуется тем же токеном через subprotocol —
  заголовки браузерному WebSocket задать нельзя.
- **Картинки и файлы.** `<img src>` не умеет слать `Authorization`, поэтому нативный
  клиент берёт короткоживущий билет (`/api/media-ticket`) и подставляет его в query к
  `/uploads`. Билет живёт полсуток и умирает вместе с сессией.
- **Ключи E2E.** В нативной сборке приватные ключи и токен лежат в Keychain, а не в
  хранилище WebView: iOS считает его кэшем и вправе вычистить при нехватке места, а вместе
  с ключом человек потерял бы доступ ко всей переписке.

### Шаги на Mac

```bash
npm install
VITE_API_URL=https://your-server.example npm run build
npx cap add ios
npm run ios:sync
npm run ios:open
```

`VITE_API_URL` обязателен: без него клиент пойдёт по относительным путям, а в WebView
это `capacitor://localhost`, где никакого сервера нет.

Дальше в Xcode:

1. **Signing & Capabilities** → выбрать команду разработчика, задать Bundle Identifier
   (тот же, что `appId` в `capacitor.config.ts` и `APNS_BUNDLE_ID` на сервере).
2. Добавить capability **Push Notifications** и в **Background Modes** включить
   *Remote notifications*.
3. В `ios/App/App/Info.plist` добавить пояснения к разрешениям — без них приложение
   падает при первом же обращении к камере или микрофону:

```xml
<key>NSCameraUsageDescription</key>
<string>Камера нужна для видеозвонков и съёмки фото в чат</string>
<key>NSMicrophoneUsageDescription</key>
<string>Микрофон нужен для звонков и голосовых сообщений</string>
<key>NSPhotoLibraryUsageDescription</key>
<string>Доступ к фото нужен, чтобы отправлять их в чат</string>
```

4. Product → Archive → Distribute App: для TestFlight и App Store нужен платный
   Apple Developer Program ($99/год), для установки на собственное устройство хватит
   бесплатного Apple ID (подпись протухает через 7 дней).

### Что осталось за пределами этой обвязки

- **Голосовые сообщения.** Safari пишет `MediaRecorder` в mp4/aac, а не в webm; сервер
  этот тип принимает (`audio/mp4`), но на устройстве это стоит проверить отдельно.
- **Требования App Store к мессенджерам.** Блокировка пользователей и удаление аккаунта
  из приложения уже есть; для публикации остаётся политика конфиденциальности и механизм
  жалоб на контент (Guideline 1.2). Для сборки «для себя» не нужно.

## Звонки при закрытом приложении (CallKit + PushKit)

Обычный WebRTC-звонок требует, чтобы у собеседника было открыто приложение с живым
сокетом. На iOS это почти всегда не так: систему усыпляет приложение через несколько
секунд после сворачивания. Поэтому входящий звонок на закрытое приложение идёт другим
путём.

### Как это работает

1. Звонящий шлёт `call_invite`. У собеседника нет ни одного сокета — сервер проверяет,
   есть ли у него устройство с токеном PushKit. Если нет (человек только в браузере),
   звонящий сразу получает «недоступен», как и раньше.
2. Сервер придерживает SDP-оффер и отправляет **VoIP-пуш** — отдельный тип APNs с
   топиком `<bundleid>.voip`, который будит даже выгруженное из памяти приложение.
3. Нативный слой обязан немедленно показать входящий звонок через CallKit: iOS убивает
   процесс, если этого не произошло, и после нескольких нарушений вообще перестаёт
   доставлять VoIP-пуши. Поэтому CallKit и PushKit живут в `CallCenter`, который
   стартует из AppDelegate, — WebView к этому моменту может ещё не существовать.
4. Приложение поднимается, подключает сокет и просит у сервера отложенное приглашение
   (`call_claim`). Вместе с оффером приезжают ICE-кандидаты, накопившиеся за время
   пробуждения — иначе соединение собиралось бы заметно дольше.
5. Человек жмёт «Принять» на системном экране — запускается обычный приём звонка.
   Если он успел нажать раньше, чем приглашение доехало, приём ждёт его и срабатывает
   сам.

Если разбуженное устройство не отозвалось за 25 секунд, звонок закрывается как
несостоявшийся — значит, пуш не дошёл.

Режим «не беспокоить» для звонков выключает регистрацию токена PushKit целиком: будить
телефон, чтобы тут же сбросить звонок, смысла нет.

### Настройка в Xcode

Плагин лежит в репозитории (`native-plugins/callkit`) и подключён как обычная
зависимость — `npm run ios:sync` подхватит его сам. Отдельно нужно:

1. **Signing & Capabilities** → добавить **Push Notifications**, а в **Background Modes**
   включить *Voice over IP* и *Remote notifications*.
2. В `ios/App/App/AppDelegate.swift` запустить `CallCenter` до всего остального —
   иначе VoIP-пуш придёт в приложение, которое ещё не готово его показать:

```swift
import CornetCallKit

func application(_ application: UIApplication,
                 didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
    CallCenter.shared.configure()
    return true
}
```

Ключ APNs для VoIP-пушей — тот же, что и для обычных (см. раздел про APNs выше);
отдельный сертификат при token-based авторизации не нужен.

### Чего ждать на устройстве

Звук в звонке ведёт WebRTC внутри WKWebView, своей аудиоединицей приложение не
управляет — а CallKit рассчитывает как раз на обратное. На практике это работает, но
именно этот стык (переключение на динамик, поведение при перехвате сессии обычным
телефонным звонком) — первое, что стоит проверить на живом устройстве, и первое, что
может потребовать доводки.

## Удаление аккаунта

Настройки → Безопасность → «Удаление аккаунта». Требование App Store (Guideline 5.1.1v),
но в первую очередь — честное поведение: «удалить» должно означать удалить, а не отключить.

Подтверждений три: текущий пароль, код второго фактора (если он включён) и имя
пользователя, набранное вручную. Последнее не паранойя — от случайного нажатия пароль,
подставленный менеджером паролей, не спасает.

Что происходит на сервере (одной транзакцией — аккаунт, удалённый наполовину, хуже
неудалённого):

- строка пользователя удаляется, и по внешним ключам с ней уходят сессии, сообщения,
  реакции, голоса в опросах, ключи шифрования, папки, блокировки и устройства для пушей;
- **личные чаты удаляются целиком, у обеих сторон.** Это осознанный выбор: переписка один
  на один без одной стороны нерабочая — писать в неё некому, ключа для расшифровки нет, а
  сообщения ушедшего и так исчезли. Остался бы чат-призрак, в котором ничего нельзя
  сделать;
- группы продолжают жить у остальных участников, исчезают только сообщения ушедшего;
  группа без единого участника удаляется;
- загруженные файлы, аватары и обложки стираются с диска, а не остаются висеть в
  `UPLOADS_DIR`;
- приватные ключи E2E стираются и на самом устройстве. При обычном выходе они намеренно
  остаются — без них не прочитать собственную историю после повторного входа, — но у
  удалённого аккаунта читать уже нечего.

Собеседники узнают об исчезновении чата сразу по сокету, а не после перезагрузки.

## Жалобы на контент

Требование App Store к приложениям с пользовательским контентом (Guideline 1.2):
пожаловаться должно быть можно, и жалоба должна куда-то приходить.

Пожаловаться можно из двух мест: контекстное меню чужого сообщения → «Пожаловаться»
и карточка профиля → «Пожаловаться». Блокировка пользователя была и раньше и никуда
не делась.

Жалоба всегда сохраняется в таблицу `reports`; письмо оператору (`ALERT_EMAIL`) —
дополнение, его недоставка не может потерять жалобу. Письма троттлятся до одного в
минуту, поэтому в каждом указано общее число нерассмотренных.

Пожаловаться можно только на то, что человек и так видит: жалоба на сообщение
проверяет, что жалующийся состоит в том чате. Иначе по номеру сообщения можно было бы
разведывать чужие переписки.

**Текст жалобы снимается на устройстве.** В зашифрованных чатах у сервера есть только
шифротекст, поэтому форма прикладывает расшифрованную копию — её видно в самой форме, и
её можно не прикладывать. Проверить подлинность такой копии сервер не может, и в выводе
для оператора она честно помечена как «со слов жалующегося».

### Разбор жалоб

Отдельной админки в приложении нет намеренно: для неё нужна роль администратора,
отдельный вход и отдельная поверхность атаки. Оператор и так ходит на сервер:

```bash
cd server && npm run reports
```

```bash
cd server && node src/moderation.js --close 12
```

`--all` показывает и уже рассмотренные.

## Политика конфиденциальности

Живёт по публичному адресу `/privacy` — открывается без входа в аккаунт, потому что
ревьюер App Store открывает её просто по ссылке. Внутри приложения на неё ведут ссылки
с экрана входа и из «О приложении».

Текст описывает то, что действительно делает код: что хранится, что сервер видит и чего
не видит, кому уходят данные, сколько живут сессии и ссылки, как удалить аккаунт.

**Перед публикацией заполните `OPERATOR` в `src/components/PrivacyPolicy.tsx`** — имя
оператора, адрес для связи и юрисдикцию. Пока они пустые, страница честно показывает
«не указано» вместо выдуманных данных; для App Store адрес для связи обязателен.

Это описание фактов, а не проверенный юристом документ. Если приложение выходит за
пределы личного использования, текст стоит показать юристу — особенно в части GDPR.

## Шифрование вложений

Сквозное шифрование раньше покрывало только текст: файлы уходили на сервер как есть, и
обещание «переписку не прочитать» на картинки и документы не распространялось. Теперь в
зашифрованных чатах вложения шифруются тоже.

Как устроено:

1. Файл шифруется на устройстве отдельным одноразовым ключом (AES-256-GCM) — свой ключ на
   каждый файл, а не общий на переписку.
2. На сервер уезжает шифротекст под именем `attachment.bin` с типом
   `application/octet-stream`.
3. Ключ, настоящее имя и настоящий тип едут **внутри конверта сообщения** — то есть уже
   зашифрованными для получателя и подписанными отправителем. Отдельного поля в конверте
   нет намеренно: иначе его пришлось бы заново заводить под подпись.
4. Получатель расшифровывает конверт, скачивает шифротекст, расшифровывает его в памяти и
   отдаёт в `<img>`/`<video>` как blob-ссылку.

Полезная нагрузка конверта версионирована (`src/crypto/payload.ts`): сообщения без
вложения кодируются ровно как раньше, голым текстом, поэтому вся старая переписка
продолжает читаться. Как только появляется файл, строка начинается со служебного префикса
с управляющим символом U+0001 — набрать такой в поле ввода нельзя, спутать с текстом
человека невозможно.

Картинки и голосовые расшифровываются сами, видео и документы ждут нажатия: тянуть по
25 МБ на каждое открытие чата — издевательство над мобильным трафиком.

**Что сервер всё же узнаёт:** размер файла, время загрузки и категорию вложения (фото,
видео, голосовое, документ) — она остаётся в открытом виде, чтобы сообщение можно было
показать до расшифровки. Имя файла, его тип и содержимое серверу недоступны.
